## Working Mode

Work on one requested task at a time.

Before editing:

1. Read the imported project context.
2. Check the current phase in `docs/project-plan.md`.
3. Inspect the relevant existing files and tests.
4. Confirm the requested change is inside the documented product and architecture boundaries.
5. Identify the smallest complete change needed.

Do not continue into the next task or project phase unless explicitly asked.

If a request conflicts with the project documents, stop and explain the conflict before changing code.

If a material product or architecture decision is missing, stop and ask rather than inventing one.

## Task Execution

For implementation work:

1. inspect before editing,
2. make a short plan,
3. change only the files required for the task,
4. add or update the relevant tests,
5. run the appropriate verification commands,
6. review the final diff,
7. update documentation only when the implemented behavior or an accepted decision changed,
8. update `docs/project-plan.md` only after the work is verified.

Do not perform opportunistic refactors.

Do not add abstractions, dependencies, folders, services, or infrastructure because they may be useful later.

Do not mark planned work complete based on partial implementation.

## Verification

Use the checks appropriate to the change.

Frontend changes may require:

```text
npm run lint
npm run test
npm run build
```

Use only commands that actually exist in `frontend/package.json`. Do not invent scripts.

Backend changes may require:

```text
uv run pytest
uv run ruff check .
uv run mypy ...
```

Use only tools and commands configured in the repository. If a required check is not configured yet, report that instead of pretending it ran.

For database work, verify migrations against a real PostgreSQL development/test database when the current phase provides one.

For AI work, normal automated tests must use mocked/provider-independent boundaries. Do not make live model calls in routine test runs.

Never report a test, build, migration, command, or deployment as successful unless it actually completed successfully.

## Documentation Discipline

The project documents have separate responsibilities:

- `requirements.md` — product behavior and scope
- `decisions.md` — accepted choices and trade-offs
- `architecture.md` — technical structure and responsibility boundaries
- `ai-usage.md` — product AI rules and meaningful AI-assisted development record
- `project-plan.md` — execution status and phase tracking

Do not move content between these documents casually.

Do not rewrite a document merely to improve wording while implementing unrelated code.

Do not change an accepted requirement or decision indirectly through code. If implementation reveals that a documented decision must change, surface it first.

## AI-Assisted Development

Claude is a development tool, not the product owner.

Do not:

- invent requirements,
- make undocumented business decisions,
- weaken tests to make code pass,
- introduce technology to make the project look more sophisticated,
- add comments explaining that code was generated by AI,
- add Claude/AI signatures,
- add prompt text or scratch analysis to the repository,
- add `Co-Authored-By` trailers unless explicitly requested.

Meaningful AI-assisted engineering work should be recorded only as defined in `docs/ai-usage.md`.

The repository should read like a normal, carefully engineered product repository.

## Git Operations

Do not commit, push, amend, rebase, force-push, or rewrite history unless the user explicitly asks for that Git operation.

Before a requested commit:

1. inspect `git status`,
2. inspect the relevant diff,
3. confirm no secrets or generated files are included,
4. stage only intended files,
5. use the exact commit message requested when one is provided.

Never include unrelated changes in a commit.

## Cross-Platform Work

The repository is used on both Windows and macOS.

Prefer cross-platform project configuration and commands where practical.

Do not introduce code or scripts that depend on one developer machine, absolute local paths, or OS-specific behavior unless the project explicitly requires it.

Repository text files use LF line endings as defined by `.gitattributes`.

## Response After a Task

When a task is complete, report concisely:

- what changed,
- files changed,
- verification commands actually run and their results,
- any unresolved issue or decision,
- whether the current project-plan item is complete.

Do not start the next task automatically.
